## 2. Chat API 的请求结构（读懂 JSON 才能干活）

```json
POST https://open.bigmodel.cn/api/paas/v4/chat/completions
{
  "model": "glm-4-flash",            // 用哪个模型（glm-4-flash 免费）
  "messages": [                       // 对话历史，按顺序排列
    {"role": "system", "content": "你是严格的测试工程师"},   // 人设/规则，最优先
    {"role": "user", "content": "判断这条消息的意图"}         // 用户输入
  ],
  "temperature": 0.7,                 // 采样温度：随机性（今天的主角）
  "max_tokens": 200                   // 输出上限，控制成本
}
```

**三个必须懂的字段**：

| 字段 | 作用 | 训练师视角 |
| --- | --- | --- |
| `messages` 角色 | system=规则，user=输入，assistant=历史回复 | 评测脚本里 system 放"评分细则"，user 放被测内容 |
| `temperature` | 0=几乎确定性输出，1+=高随机 | **评测必须用低温度（0~0.2）保证可复现**；创作类才用高温 |
| `max_tokens` | 输出长度上限 | 成本闸门；截断会破坏 JSON 输出，评测时注意 |

## 3. 工程三件套（脚本里已实现，看懂即可）

1. **重试 + 指数退避**：请求失败等 2s、4s、8s 再试——API 限流是常态，不重试的评测脚本跑不完 500 条
2. **Key 安全**：从环境变量读 `ZHIPU_API_KEY`，**永远不写死在代码里**（面试会问安全意识）
3. **成本/用量统计**：每次记录 token 用量，跑批前先算"这一轮评测要花多少钱"

## 4. 今日实验：temperature 对比

固定同一个 Prompt（"用一句话解释什么是过拟合"），temperature 取 0 / 0.7 / 1.5 各跑 3 次：

- 记录：3 次输出是否相同、内容质量是否稳定
- **预期结论**：温度 0 → 3 次几乎一样；1.5 → 措辞飘忽甚至胡说
- **迁移到工作**：评测集回归要可复现 → `temperature=0`；想测模型稳定性 → 同一输入跑 5 次看输出方差（这本身就是一种评测维度！）

## 5. API Key 配置（5 分钟，没有 Key 用 mock）

```bash

# 3. 验证
```
