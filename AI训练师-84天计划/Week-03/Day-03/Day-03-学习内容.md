## 2. 为什么校验比"祈祷格式正确"重要

LLM 输出结构化数据的失败模式有四种，必须分层防御：

| 失败模式 | 例子 | 防御层 |
| --- | --- | --- |
| ① 完全不是 JSON | "好的，以下是结果：…" | 抠 `{...}` 块（D1 的正则） |
| ② JSON 但字段缺失 | `{"intent": "投诉"}` 少了 confidence | Schema 校验 |
| ③ 字段值非法 | intent="牢骚"（不在枚举里） | 值域校验 |
| ④ 类型错误 | confidence="很高"（应为数字） | 类型校验 |

**重试的关键技巧**：把校验错误信息塞回提示词再问一次——`"你上次输出缺少 confidence 字段，请修正"`。模型看到自己错在哪，修复成功率远高于原样重问。

## 3. 校验函数的设计（手动实现，理解原理）

不引入 pydantic（先理解原理，W6 若需要再加）：一个 schema 就是一个嵌套 dict，声明每个字段的类型、必填性、值域。校验器递归走一遍，收集**全部**错误（不要遇错即停——一次给全错误信息，重试修复率更高）。

## 4. 今日代码（`day03_json_output.py`）

- 定义评测结果的 schema：`{intent: 枚举, confidence: 0-1 数字, reason: 字符串}`
- 主流程：生成 → 校验 → 失败则带错误重试（最多 2 次）→ 记录每轮状态
- 实验模式 `--inject`：人为把模型输出换成坏 JSON，观察重试闭环是否兜住——**测试思维：不注入故障怎么验证容错逻辑？**

## 6. 与测试工作的类比（面试口语）

- Schema 校验 ≈ 接口测试的响应断言——**你写过多少次 assert response["code"] == 0？同一个肌肉记忆**
- 错误信息回喂重试 ≈ 缺陷单里"复现步骤+期望结果"写清楚，开发才修得快——**报错要具体，模型和人都一样**
- --inject 故障注入 ≈ 混沌测试/异常测试——**不注入坏数据，永远不知道容错代码跑没跑过**
