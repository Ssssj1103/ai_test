# 验证 · Day 17 · 结构化输出闭环

## 一、自测题（口答）

1. 为什么校验器要"收集全部错误"而不是"遇错即停"？
2. 重试 2 次仍失败的记录，你打算怎么处理？（评测场景 vs 生产场景分开说）
3. 原生 JSON mode（response_format）和提示词方案各有什么局限？
4. confidence 字段校验除了"是数字"，还应检查什么？为什么 0-1 范围检查必要？
5. 如果模型 100% 输出合法 JSON，重试逻辑就永远不触发——你怎么证明重试代码是对的？

<details><summary>参考答案</summary>

1. 一次修一个错要 2-3 轮重试（token 和时间翻倍）；一次给全错误清单，模型一轮修完。原则同缺陷报告：一次汇报所有问题，别挤牙膏。
2. 评测场景：标记为 FAILED 保留在结果里并单独统计失败率（失败率本身是质量指标），绝不静默丢弃；生产场景：降级路径（默认值/人工队列），并告警。
3. 原生 JSON mode：格式保证但不校验值域和必填（能输出合法 JSON 但字段乱来），且部分模型/版本不支持；提示词方案：灵活可控但格式可能漂移。生产常用组合：JSON mode 保底 + 自己的 schema 校验兜底。
4. 还应检查值域（0~1）和精度合理性。模型可能输出 confidence=15（越界）或 "0.85"（字符串）——不校验值域，下游阈值过滤会把 confidence=15 当"极高置信"全放行，污染评测结果。
5. 这正是 --inject 的意义：把"输出坏了"变成可控实验条件。故障注入是验证容错代码的唯一可靠手段——同理于你测 try/except 时必须真的造异常。
</details>
