# 验证 · Day 18 · 批量调用工程

## 一、自测题（口答）

1. GIL 存在为什么线程池仍然有效加速 API 批量调用？
2. 断点续跑的前提是什么？如果同一条任务两次运行结果不同会怎样？
3. 重试要不要对"4xx 客户端错误"（如 401 无权限）做指数退避？为什么？
4. 怎么在不跑全量的情况下估算 1000 条任务的 token 成本？误差来源有哪些？
5. 并发数开到 50 会发生什么？你怎么找到合适的并发数？

<details><summary>参考答案</summary>

1. 线程在等待网络响应时释放 GIL，其他线程可继续发请求。瓶颈是 I/O 等待而非 CPU 计算，所以线程池有效；CPU 密集任务才需要进程池。
2. 前提：任务结果与执行顺序/次数无关（幂等）+ 结果文件按任务唯一键去重。若结果非确定（如高温采样），续跑会让"同一任务"在不同运行里有不同结果——评测任务应低温保证幂等。
3. 不该。401/400 是确定性错误（Key 无效/参数错），重试 100 次结果一样，纯浪费；只有 429（限流）和 5xx/网络错误（临时性）才值得退避重试。重试策略要区分错误类型——和你写自动化脚本的 retry 逻辑同理。
4. 抽样：随机取 20-30 条，跑出实际 token（输入+输出），算均值±标准差，外推全量并加上 20-30% 余量。误差来源：输出长度方差（大头）、偶发长回答、重试带来的重复消耗。
5. 触发 429 限流，重试风暴让整体更慢甚至被封。方法：阶梯实验（4→8→16 观察吞吐和 429 率），选"吞吐不再上升而 429 出现"之前的值；不同服务商限额不同，要实测。
